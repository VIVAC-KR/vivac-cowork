# 데이터 파이프라인 & 신뢰도 정책

> 원본: `docs/data-pipeline.md`(필드 설계 확정 문서, 2026-07-11) + 이후 구현 사항. Enum 원시값은 [`../devel/01-data-model.md`](../devel/01-data-model.md), 배치 구현은 [`../devel/04-async-jobs.md`](../devel/04-async-jobs.md) 9장 참고.

## 1. 왜 두 개의 축이 필요한가

스팟 데이터에는 서로 다른 질문에 답하는 두 개의 상태 필드가 있다.

| 필드 | 질문 | 답이 결정하는 것 |
|---|---|---|
| `pipeline_status` | 이 데이터가 어느 처리 단계까지 왔는가 | **노출 여부** (`PUBLISHED`만 서비스에 보임) |
| `trust_tier` | 이 데이터를 얼마나 믿을 수 있는가 | **노출 후 신뢰도 표시 + 운영팀 보강 우선순위** |

두 필드는 독립적이다 — `PUBLISHED`된 스팟도 tier 3(미검증)일 수 있고, 이는 의도된 정책이다(§3).

## 2. pipeline_status 단계 정의

| 단계 | 의미 | 진행 방향 |
|---|---|---|
| `RAW` | 크롤링/수집한 원본 그대로 | 신규 row의 기본값 |
| `ENRICHED` | 크롤링 기반 자동 보정·병합 완료 | RAW 다음 |
| `CURATED` | 사람이 정제·입력 완료 | 검수 대기 상태 |
| `REVIEWED` | 검수자 승인 완료 | 공개 직전 |
| `PUBLISHED` | production API에 노출 | 최종 단계 |
| `REJECTED` | 검수 반려, 중복, 폐쇄된 스팟 등 | 언제든 여기로 되돌아갈 수 있음 |

기존에 서비스 중이던 데이터는 마이그레이션 시점에 전부 `PUBLISHED`로, `trust_tier`는 `NULL`(미판정)로 시작했다.

## 3. trust_tier — 노출 후에도 남는 신뢰도 문제

| 등급 | 기준 |
|---|---|
| 1 | 공식 소스 + 4대 핵심 속성(화기/접근성/편의시설/예약) 모두 채워짐 |
| 2 | 신뢰 가능한 소스지만 일부 속성 누락, 또는 커뮤니티 소스지만 교차 확인됨 |
| 3 | 단일 비공식 소스, 미검증 |

### 노출 정책

`PUBLISHED`면 tier 3도 노출한다 — 노지/비박 커버리지가 서비스의 차별화 포인트이므로, 데이터가 부족하다고 숨기는 대신 "미검증" 뱃지로 투명하게 보여주는 쪽을 택했다. 단, 화기 가능 여부 같은 **안전 관련 속성**은 tier 3일 때 프론트에서 일괄 "확인되지 않음"으로 표시한다. 필드 단위로 개별 검증 플래그를 매기는 것은 현재 과설계로 판단해 도입하지 않았다.

### 신선도 — 시간이 지나면 신뢰도가 떨어진다

한 번 매겨진 `trust_tier`가 영원히 유지되면 "6개월 전엔 정확했지만 지금은 아닌" 정보가 계속 신뢰 딱지를 달고 있게 된다. 이를 막기 위해:

- `last_verified_at`(마지막 검증 시각) 컬럼을 도입했다.
- 180일이 지난(또는 한 번도 검증된 적 없는) `PUBLISHED` 스팟은 주 1회 배치로 자동 처리된다:
  - tier 1/2 → 한 단계 하향
  - 이미 tier 3인 경우 → 검증 담당자 배정을 해제해 재검증 대기열로 되돌림(공개 상태는 유지)

**현재 공백**: 스팟이 실제로 재검증됐을 때 `last_verified_at`을 갱신해주는 쓰기 경로가 아직 없다 — 운영팀이 검수 화면에서 `trust_tier`를 다시 매겨도 "언제 검증했는지"는 자동으로 기록되지 않는다. 이 부분이 채워져야 신선도 정책이 완전히 작동한다.

## 4. 운영 활용 예시

- tier 3인데 조회수가 높은 스팟 = 검증 우선순위 1순위 (사용자 관심은 높은데 신뢰도가 낮은 데이터)
- 재검증 대기열로 자동 편입된 스팟은 My Queue에서 신규 배정 대상이 된다

## 5. 아직 결정되지 않은 것

- **ETL 재적재 시 pipeline_status 강등 위험**: 외부 데이터 파이프라인이 이미 `PUBLISHED`인 스팟을 재적재할 때, payload에 `pipeline_status`가 포함돼 있으면 실수로 등급이 되돌아갈 수 있다. ETL 쪽에서 이 필드를 아예 payload에서 빼는 원칙으로 갈지, 코어 백엔드가 강등을 차단할지 아직 정하지 않았다.
- **trust_tier 자동 판정**: 현재는 사람이 수동으로 등급을 매긴다. 소스별 기본값 + 4대 속성 완비 여부를 기준으로 한 자동 판정 로직은 아직 없다.
- **재검증 시 last_verified_at 갱신 경로**: §3의 공백 참고.
