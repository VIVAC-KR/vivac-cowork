# 운영 콘솔 & 내부 운영 프로세스

> 대상: 운영팀 리드, 콘텐츠 운영자, 신규 스태프 온보딩. 개발자 관점 API 상세는 [`../devel/02-api-reference.md`](../devel/02-api-reference.md) §4, [`../devel/03-auth-and-security.md`](../devel/03-auth-and-security.md) 참고.

## 1. vivac-console이란

내부 운영팀 전용 웹 화면(별도 저장소, Next.js + Refine). **DB에 직접 접속하지 않고** 항상 `vivacapi-core`의 `/v1/internal/*` API를 경유한다 — 이렇게 함으로써 콘솔에서의 조작도 일반 서비스와 동일한 검증·정합성 규칙을 통과하게 만든다. "콘솔은 화면만, 데이터 규칙은 백엔드 한 곳에"가 원칙이다.

로그인은 회사 Google 계정(도메인 화이트리스트) + 백엔드에 등록된 `is_staff=True` 계정만 통과한다. 회사 도메인 계정이어도 백엔드에서 staff로 등록되지 않으면 콘솔을 쓸 수 없다.

## 2. 운영 인력 권한 등급

| 등급 | 전형적 업무 |
|---|---|
| **STAFF** | 스팟/그룹 목록 조회, 상세 열람, 메타 정보 수정, 검증 대기열에서 담당 스팟 검수, 이미지 업로드, 데이터 이력 조회 |
| **MANAGER** | 위 + 검증 담당자 배정/재배정(휴가·퇴사·물량 쏠림 대응), 그룹 삭제, 그룹 멤버 강제 편입/역할 변경, 옵션 화이트리스트(카테고리/편의시설 등) 관리 |
| **SUPERUSER** | 위 + 스팟 대량 upsert(최대 5000행) — 외부 소스에서 대량 데이터를 한 번에 적재하는, 잘못되면 파급이 큰 작업 |

등급 배정은 API로는 불가능하고 DB 직접 조작 또는 SQLAdmin으로만 이뤄진다 — 초기 단계의 의도적인 공백(신규 스태프 승격은 신뢰할 수 있는 인원이 수동으로 처리).

## 3. 데이터 검증 파이프라인 운영

스팟 데이터는 아래 흐름을 통과해야 실제 서비스에 노출된다. 자세한 단계 정의는 [01-domain-glossary.md](./01-domain-glossary.md) 참고.

```
외부 소스 수집(RAW) → 자동 보정(ENRICHED) → 수작업 정제(CURATED)
    → 검수(REVIEWED) → 공개(PUBLISHED)
                              ↓ (문제 발견 시)
                          REJECTED / CURATED로 반려
```

### 3.1 My Queue — 검증 담당자별 대기열

콘솔 대시보드에 담당자별 검증 대기 물량(My Queue)이 표시된다. `MANAGER` 이상 권한자가:

- **초기 배정**: 아직 아무에게도 배정되지 않은 스팟을 특정 담당자에게 할당
- **재배정/해제**: 이미 배정된 스팟을 다른 담당자로 옮기거나 배정을 해제
- **물량 이전**: 특정 담당자(A)에게 몰린 검증 대기 물량 중 일부를 다른 담당자(B)에게 통째로 옮기기 — 휴가·퇴사·업무 재배분 시나리오를 위한 기능

### 3.2 데이터 이력 조회

스팟/사업자정보의 모든 변경(생성/수정/삭제)은 자동으로 이력에 남는다(감사 로그). 누가, 언제, 무엇을 바꿨는지 콘솔에서 조회할 수 있다 — 다만 현재는 최신 100건 고정이라 그 이전 이력은 조회 UI가 없다.

### 3.3 대량 데이터 적재 (Bulk Upsert)

외부 소스(고캠핑, 산림청 등)에서 받은 데이터를 엔지니어가 JSON으로 일괄 등록한다. `SUPERUSER` 권한만 가능 — 최대 5000행까지 한 번에 처리되는 만큼 실수 시 파급이 크기 때문이다. 처리는 백그라운드에서 이뤄지고 콘솔에서 진행 상황(성공/실패, 실패 사유)을 확인할 수 있다. 행 단위 부분 실패는 허용하지 않는다 — 하나라도 실패하면 전체가 롤백된다.

## 4. 콘텐츠 모더레이션

- **리뷰 신고**: 유저가 신고한 리뷰가 콘솔에 모인다. 부적절한 콘텐츠 판단은 운영팀 재량.
- **그룹 모더레이션**: `MANAGER` 이상은 아무 유저의 그룹이나 조회·수정·삭제할 수 있고, `PRIVATE` 그룹에도 개입할 수 있다(일반 유저 API에서는 불가능한 예외). 신고된 공개 그룹을 비공개로 강제 전환하는 등의 조치가 가능하다.
- **스팟 소프트 삭제/복구**: `MANAGER` 이상이 스팟을 (하드 삭제가 아닌) 소프트 삭제할 수 있고, 실수 시 복구도 가능하다.

## 5. 이미지 운영

스팟 사진은 운영팀이 콘솔을 통해 업로드한다(일반 유저의 사진 UGC는 아직 없음). 업로드는 3단계(업로드 URL 발급 → 클라이언트가 직접 스토리지에 업로드 → 등록 확인)로 나뉘어 있어, 실제로 파일이 올라갔는지 서버가 재확인한 뒤에만 이미지가 등록된다.

## 6. 화이트리스트 관리 (카테고리/편의시설 등)

스팟의 카테고리, 편의시설, 주변시설, 장비대여 옵션은 자유 텍스트가 아니라 관리형 화이트리스트다. `MANAGER` 이상이 콘솔에서 새 옵션값을 추가/삭제할 수 있다 — 검색·필터가 이 화이트리스트를 기준으로 동작하므로, 값이 중구난방으로 늘어나는 것을 막기 위한 장치다.

## 7. 운영 관점에서 아직 없는 것

- **스팟 자체 신고(폐쇄/접근불가)**: 리뷰 신고는 있지만, 노지 스팟이 사유지화·산불통제 등으로 조용히 폐쇄됐을 때 이를 신고받아 재검증 큐로 자동 편입시키는 기능이 없다. 검증 담당자 재할당 기능(§3.1)이 선행돼 있어야 신고 급증 시 병목 없이 대응 가능하다.
- **staff 등급별 SQLAdmin 제한**: `/admin`(SQLAdmin)은 아직 등급을 구분하지 않는다 — staff이기만 하면 다른 유저의 계정 상태를 전부 토글할 수 있는 단일 평면이다.
- **audit_log 대상 확장**: `users` 테이블은 아직 감사 로그 대상이 아니다.
