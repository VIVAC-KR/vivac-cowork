## 1부. 정상 구현 — 확정 스펙 기록

이미 화면·API가 다 있고 정상 동작을 확인했다. 여기서는 회귀 방지를 위해 현재 스펙을 기록만 한다 — 새 기획이 아니다.

### 1.1 홈 — 추천 야영장 캐러셀

- **현재 스펙**: 가로 스크롤 카드 5개+, 각 카드에 신뢰도 배지("정보 확인됨"/"공식 인증" 등 `trust_tier` 기반) + 카테고리("자연휴양림" 등) + 이름. 클릭 시 `/spots/{uid}`로 이동.
- **데이터 소스**: `GET /v1/explore/spots`(추천 로직은 미확인 — 단순 최신순/랜덤인지 별도 랭킹인지 코드 확인 필요, ⚪).
- **빈 상태/에러**: 미확인 — API 실패 시 폴백 UI 존재 여부 확인 필요.

### 1.2 스팟 상세 (`/spots/{uid}`)

- **현재 스펙**: 제목, 사이트 유형·사이트 수·평균 면적·화로 유형(스펙 그리드), 이용요금, 위치(지도 없이 텍스트/버튼만), 시설(편의시설/주변시설/렌탈장비), 후기 섹션, "웹사이트 열기" 버튼.
- **데이터 소스**: `GET /v1/explore/spots/{uid}` (`SpotDetail`) — `uid, title, address, address_detail, website_url, trust_tier, tagline, category, themes, is_fee_required, is_pet_allowed, features, camp_sight_type, unit_count, total_area_m2, fire_pit_type, latitude, longitude, description, amenities, nearby_facilities, has_equipment_rental, phone, booking_url, image_url, rating_avg, review_count`.
- **🔴 확인된 문제(기획 아님, 데이터 이슈)**: 실제 표본에서 대부분 필드가 `null` — "정보 없음"이 대량 노출된다. 이건 화면 기획 문제가 아니라 §7(운영/데이터) 이슈로 별도 관리 필요.

### 1.3 검색 (`/search?q=`)

- **현재 스펙**: 검색창(상단 고정), 결과 리스트(카드형, 지역·트러스트 배지 포함), 좌측 필터 패널(카테고리 칩, 지역 칩). "총 N곳" 카운트 표시.
- **데이터 소스**: 탐색 API의 `q` 파라미터(§`core/projects/spot-search-postgres-fts.md` — pg_trgm+tsvector).
- **미검증**: 필터 칩 클릭이 실제로 결과를 좁히는지(상호작용까지는 이번 점검에서 확인 못 함) — 🟠 확인 필요.
- **홈 검색창과의 단절**: 홈 화면 검색창에 직접 타이핑 후 Enter가 `/search`로 안 넘어가는 현상을 관찰함(§2.2와 연결된 문제일 수 있음) — 🔴 재현·원인 확인 필요.

### 1.4 로그인 (`/login`)

- **현재 스펙**: Google 소셜 로그인 버튼 단일. NextAuth v5 서버 세션.
- **참고**: `front/backlog/codebase-review-260714.md` Tier1에 이 플로우 관련 미해결 보안 이슈(access token 브라우저 노출, secret 주입 누락)가 있음 — 화면 기획과 별개로 STATUS.md §2 참고.

## 2부. 반쪽 구현 — 마무리 기획

### 2.1 홈 — "이번 주 인기 박지" 캐러셀 🔴

**문제**: 카드는 렌더링되지만 링크가 `/spots/spot-101`~`spot-106` 같은 하드코딩 placeholder ID라 전부 클릭하면 404. `homePlaceholderData.ts`에서 나오는 정적 목데이터로 추정.

**막힌 이유**: "인기"를 산정할 근거 자체가 백엔드에 없다. `booking_url` 클릭, 조회수, 저장 수 등 어떤 이벤트도 트래킹되지 않는다(`business-feature-roadmap.md` 3.1에서 이미 "click/analytics/event_log 검색 결과 0건"으로 확인됨).

**기획 옵션** (택1, 팀 결정 필요):

| 옵션 | 설명 | 구현 비용 |
|---|---|---|
| A. "인기" 재정의 → "최근 등록" | 트래킹 인프라 없이 `created_at`/`pipeline_status` 전이 시점 기준 최신 PUBLISHED 스팟으로 대체 | 하 — 즉시 가능 |
| B. 실제 인기 집계 도입 | 조회/저장 이벤트 로깅 인프라([2.3 찜한 스팟] 알림 기능과 인프라 공유 가능, `business-feature-roadmap.md` 2.3·3.1 참고)를 먼저 구축 | 상 |
| C. 섹션 자체를 임시 제거 | 데이터 근거가 생기기 전까지 노출 안 함 | 하 |

**권장**: 단기는 A(최근 등록으로 재정의 + 라벨을 "이번 주 인기"에서 "최근 등록된 박지"로 수정), 중기는 B. C는 최후 수단.

**다음 액션**: 어느 옵션으로 갈지 결정 → 결정되면 `docs/front/projects/`에 별도 설계 문서로 승격.

### 2.2 홈 — 카테고리 필터 칩(야영장/백패킹/자연휴양림/국립공원) 🔴

**문제**: 칩이 시각적으로는 존재하나 클릭해도 화면에 변화가 없다. 검색창 Enter 미동작(§1.3)과 같은 원인(이벤트 핸들러 미배선)일 가능성이 있다 — 코드 확인 필요.

**기획**: 칩 클릭 시 `/search?category={value}`로 이동(검색 페이지가 이미 카테고리 필터를 지원하므로 재사용). 홈에서 별도 필터링 UI를 새로 만들 필요는 없고, 기존 검색 라우트로 위임하는 것으로 충분.

**다음 액션**: 프론트 코드에서 칩 클릭 핸들러가 실제로 비어있는지 먼저 확인(기획 문제가 아니라 버그일 가능성) → 버그면 front backlog에 등록, 의도된 미완성이면 위 스펙대로 구현.

## 3부. API 선구현, 화면 없음 — 신규 화면 기획

### 3.1 그룹(컬렉션) 🟠

**현재 상태**: 백엔드에 그룹 생성/멤버관리/공개범위(`GroupVisibility`)/초대 링크가 전부 구현돼 있고(`core/projects/spot-groups-admin-api.md`, `spot-invites.md`), `PUBLIC` 그룹은 비로그인으로도 조회 가능하도록 이미 설계돼 있다. 프론트엔드에는 `/groups` 라우트 자체가 없다(404 확인).

**화면 기획 (신규)**:

| 화면 | 목적 | 핵심 요소 |
|---|---|---|
| 그룹 목록(`/groups`) | 내가 속한 그룹 탐색 | 내 그룹 리스트, "그룹 만들기" CTA |
| 그룹 상세(`/groups/{uid}`) | 그룹에 담긴 스팟 탐색·공유 | 그룹명, 멤버 아바타, 스팟 리스트(스팟 카드 재사용), 초대 링크 공유 버튼, `PUBLIC`이면 비로그인도 열람 가능해야 함(백엔드 이미 지원) |
| 그룹 생성/편집 모달 | 그룹 이름·공개범위 설정 | 이름 입력, `PRIVATE`/`PUBLIC` 토글 |
| 초대 수락 화면 | 초대 링크로 유입 시 | 그룹 미리보기 → 로그인/가입 유도 → 수락 |

**데이터 소스**: `POST/GET /v1/groups/*`, `POST /v1/invites`, `POST /v1/invites/{uid}/accept`.

**의존 관계**: 이 화면이 생기면 `business-feature-roadmap.md`의 [1.3 공개 그룹 탐색/공유 진입점], [1.4 초대 현황 대시보드], [2.1 개인 찜]과 자연스럽게 이어진다(찜은 그룹 인프라 재사용 가능 — 로드맵 2.1 근거 참고).

### 3.2 리뷰 작성 🟠

**현재 상태**: 상세페이지에 "후기" 섹션은 있지만 읽기 전용 빈 상태만 있고, 작성 진입점(버튼/폼)이 화면에서 발견되지 않았다. 백엔드는 리뷰(평점 0~10, soft delete) API가 이미 있다.

**화면 기획 (신규)**:

- 스팟 상세 "후기" 섹션에 "후기 작성" CTA 추가(로그인 필요 — 비로그인 시 로그인 유도).
- 작성 폼: 평점(0~10 또는 5점 스케일로 UI 변환), 텍스트, (선택) 사진.
- 작성 후 목록에 즉시 반영, 본인 리뷰는 수정/삭제 가능(soft delete API 대응).
- 신고 버튼(백엔드에 리뷰 신고 API `spot_review_reports` 이미 존재).

**데이터 소스**: `POST/GET /v1/spots/{spot_uid}/reviews`.

**연계**: `business-feature-roadmap.md` [4.3 리뷰 유효성 시그널("지금도 유효한가요?")]을 처음부터 폼에 포함하면 재작업을 줄일 수 있음(작성 시점에 boolean 필드 하나 추가하는 정도).

## 4부. 완전 미구현 — PRODUCT.md 핵심 기능 신규 기획

### 4.1 지도 기반 탐색 🔴 (PRODUCT.md MVP 정의 핵심)

**문제**: PRODUCT.md "기능 범위" 1번 항목("지도 기반 탐색: 주변/지역별 탐색")이 화면에 전혀 없다. `/map` 404, 상세페이지도 지도 없이 텍스트 위치 정보만 있다. `latitude`/`longitude` 필드는 스키마에 있지만 실제 값은 대부분 `null`.

**화면 기획 (신규)**:

| 화면 | 목적 | 핵심 요소 |
|---|---|---|
| 지도 탐색(신규 라우트, 예: `/map` 또는 검색 결과의 뷰 전환) | 위치 기반으로 스팟을 시각적으로 탐색 | 지도(카카오맵/네이버맵/Mapbox 중 택1 — 팀 결정 필요), 마커 클러스터링, 마커 클릭 시 하단 카드 미리보기, 현재 위치 기준 "내 주변" 버튼 |
| 검색 결과 리스트/지도 토글 | 기존 `/search` 리스트뷰에 지도뷰 추가 | 리스트↔지도 토글 버튼, 필터는 공유 |

**선행 조건**: 위경도 데이터가 실제로 채워져야 지도가 의미 있다 — 이건 화면 기획이 아니라 §7(운영/데이터) 이슈로, 지도 화면 착수 전에 데이터 채움률부터 확인 필요.

**팀 결정 필요**: 지도 SDK 선택(카카오맵 vs 네이버맵 vs Mapbox) — 국내 서비스 특성상 카카오/네이버가 유리하나 가격·쿼터 정책 비교 필요.

### 4.2 합법성 정도 + 법령 레이어 ⚪ (팀 결정 대기 — STATUS.md §4)

**문제**: PRODUCT.md가 "단순 통합은 차별점이 아니다, 전환을 만드는 건 합법성 검증"이라고 스스로 명시한 핵심 차별점인데 화면·API·데이터 전부 없다.

**착수 전 필수 선행 작업**: 데이터 실현성 스파이크(`docs/archive/planning-source/VIVAC_데이터실현성_스파이크_검증설계.md`)가 아직 미실행이다. 스파이크 결과(커버리지·정확도·갱신 latency)에 따라 화면 기획 자체가 달라진다(예: 노지 폴백률이 높으면 "합법성 정도 표기" 대신 "관할·연락처 집약"으로 가치를 재정의하는 시나리오가 스파이크 설계 문서에 이미 명시돼 있음).

**따라서 이 항목은 화면 기획을 지금 확정하지 않는다** — 스파이크 결과가 나온 뒤 이 절을 채운다. 스파이크 착수 여부부터 결정해 주세요.

### 4.3 제보 ("정보가 틀렸어요" / "새 스팟 제보") 🟡

**문제**: PRODUCT.md MVP 4순위(후순위) 항목. 화면·API 둘 다 없음 — 백엔드에 리뷰 신고는 있지만 스팟 자체에 대한 신고/제보 모델이 없다(`business-feature-roadmap.md` 4.1과 동일 갭).

**화면 기획 (신규, 후순위)**:

- 스팟 상세에 "정보가 틀렸어요" 버튼 → 간단 폼(어느 정보가 틀렸는지 선택 + 자유 텍스트).
- "새 스팟 제보"는 별도 진입점(플로팅 버튼 또는 홈/검색 결과 하단) → 이름·위치·간단 설명 입력 폼.
- 제출 시 `pipeline_status`를 재검증 큐로 되돌리는 로직과 연결(`business-feature-roadmap.md` 4.1 근거).

**의존 관계**: `business-feature-roadmap.md`의 4.4 검증 담당자 재할당(이미 완료·PR #118)이 선행돼 있어 백엔드 처리 인프라는 준비됨. 화면·제보 모델만 새로 만들면 됨.

## 5. 우선순위 종합 제안


## 6. 이번 점검 범위 밖 (별도 트랙)

- 마이페이지(`/me`) — 이 문서는 다루지 않음. §3.1(그룹)·§3.2(리뷰)가 자리잡으면 "내 그룹"·"내 리뷰" 진입점으로 자연스럽게 필요해지므로, 그때 함께 기획하는 것을 권장.
- 결제/구독(Backpackers Pro) — PRODUCT.md 수익 모델은 MVP 범위 밖으로 명시돼 있어 이번 기획에서 제외.

## 7. 이 기획과 별개로 필요한 운영 조치 (화면 기획 아님)

- 스팟 상세 필드 대부분이 `null`인 데이터 완성도 문제 — 화면을 아무리 잘 만들어도 "정보 없음"만 뜬다. ETL/운영팀 데이터 채움 작업이 화면 기획과 별도로 필요.
- 위경도 데이터 채움률 확인 — §4.1 착수 조건.
