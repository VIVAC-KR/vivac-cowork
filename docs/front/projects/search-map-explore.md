# 검색 지도 탐색 (search-map-explore)

> 작성일: 2026-08-04
> 배경: 현재 `/search`는 리스트 단일 모드입니다. 지도 기반 탐색을 추가해 목록/지도 2개 모드로 확장합니다. BE 계약(좌표·`bbox`)이 아직 없어 목(mock) 기반으로 UI를 선행 구현합니다.
> 선행 문서: [`search.md`](search.md) — 이 문서는 `search.md` §4.1·§4.2가 예고한 승격 문서입니다.
> 참고(구현 근거 아님): [`archive/spots-explore-plan.md`](../archive/spots-explore-plan.md) — 2026-07-15 폐기된 `/spots` 리스트·지도 토글 설계. 컴포넌트 분해 방식만 참고했습니다.

## 1. 한 줄 요약

검색 결과를 목록/지도 2개 모드로 탐색할 수 있게 하고, 지도와 리스트를 양방향 동기화합니다. 지도 모드는 데스크탑에서 리스트+지도 분할, 모바일에서 지도+스냅 바텀시트로 표현됩니다. BE 좌표 데이터가 준비되기 전까지 **MSW 목 기반으로 UI를 완성**하는 것이 이번 범위입니다.

## 2. 역할 정의

지도는 **탐색 도구**(새로운 장소를 발견), 리스트는 **비교 도구**(후보를 비교·결정)입니다. 두 표면의 정보 밀도와 인터랙션 설계는 이 구분을 따릅니다.

## 3. 결정 사항 요약

## 4. BE 계약 의존

요청 내역과 각 항목의 근거는 [`backlog/search-map-schema-request.md`](../backlog/search-map-schema-request.md)에 있습니다. 요약하면 좌표 필드 추가, `bbox` 파라미터, 좌표 없는 스팟 제외, `total`, 지도용 경량 응답, 커서-bbox 검증 6건입니다.

### ✅ 2026-08-05 BE 회신 — 계약 확정, 구현 완료

회신 원문: [`core/projects/explore-map-api.md`](../../core/projects/explore-map-api.md). 6건 모두 수용됐고, **요청과 다르게 확정된 3건**이 있어 FE 목을 그에 맞춰 수정했습니다(2026-08-06).

| 항목 | 요청 | 확정 | FE 영향 |
|---|---|---|---|
| 지도용 경량 응답 | `fields=map` 파라미터 | **별도 엔드포인트** `GET /v1/explore/spots/map`, 응답은 `{items, truncated}` (커서·`total` 없음) | 목 핸들러·`fetchSpotsMap`·스키마 신설. `truncated=false`면 `items` 길이가 곧 전체 개수 |
| `total` 캡 | 예시 1,000 | **10,000** | 8,000건 데이터에서는 사실상 항상 정확한 값 — `총 N+곳` 표기는 당분간 도달 불가 |
| 목록 좌표 nullable | non-nullable 요청 | **nullable** — 좌표 없는 스팟 제외가 `EXPLORE_REQUIRE_COORDINATES` 플래그(기본 OFF) 뒤라, non-null 선언은 현 prod에서 거짓 | 목록은 null 분기 유지. 대신 **`SpotMapItem`의 좌표는 non-null 보장** — 핀 렌더링이 실제로 아픈 지점이라 거기에 보장을 뒀습니다 |

그 외 확정 사항: `bbox` 형식·범위 오류는 **`422 VALIDATION_ERROR`**(조용히 빈 결과를 주지 않음), 목록 `limit` 1~50 / 지도 `limit` 1~8,000(기본 8,000), 커서 스코프 불일치는 `400 CURSOR_SCOPE_MISMATCH`.

> ⚠️ **주의할 동작 변경** — 기존 `q` 없는 목록 모드가 `category`·`region_province`를 **받고도 무시**하던 버그가 함께 고쳐졌습니다. 이제 실제로 필터링됩니다. 현재 검색 화면은 `q`가 있을 때만 조회하므로 영향이 없지만, `q` 없이 필터만 보내는 호출을 추가할 때 결과가 달라질 수 있습니다.

**FE 일정의 유일한 외부 의존은 좌표 데이터 적재 시점**입니다. 적재 진척은 `GET /v1/internal/spots/stats`의 `missing_coordinates`/`total`로 추적할 수 있습니다.

## 5. 목(mock) 기반 선행 구현

### 5.1 MSW 목 사양

`packages/api/src/mocks/handlers.ts`가 현재 빈 배열(`handlers: RequestHandler[] = []`)이라 이 파일에 등록합니다.

**제공 필드** — 확정된 계약 범위까지만 채웁니다. 미확정 필드(합법·식수·취사·조용함 등)는 **의도적으로 비웁니다.** 임의로 넣으면 계약 확정 후 전부 다시 손대야 합니다.

> 2026-08-10 갱신 — 여기 열거된 4개 필드는 §6에서 **폐기**됐습니다. 배지 축은 §4.3 핵심 속성 4종입니다. 목이 비워야 할 대상도 그에 맞춰 바뀝니다.

| 필드 | 목 값 | 프로덕션 실측(2026-08-04) |
|---|---|---|
| `uid` / `title` | 프로덕션 실제 값 수집 | 정상 |
| `latitude` / `longitude` | 합성 좌표 | 전부 null |
| `trust_tier` | 1·2·3 혼합 | 전부 2 |
| `thumbnail_url` | 70% null | 전부 null |
| `region_short` | 40%만 채움 | 대부분 null |
| `category` | 20%만 채움, 코드 형식 | 대부분 null |

**재현할 서버 동작** — 데이터보다 이쪽이 중요합니다. 목이 동작까지 재현해야 UI가 실제 상황을 다루게 됩니다.

- `bbox` 사각형 내 필터링 (실제 좌표 비교 연산)
- 커서 페이지네이션 — `next_cursor` 발급·소비
- `bbox` 불일치 시 `400 CURSOR_SCOPE_MISMATCH` → FE 에러 복구 흐름 검증
- `total` 상한 캡 + `total_capped`
- 좌표 없는 스팟 제외
- 없는 uid → 404
- **인위적 지연·실패 주입** (300ms 지연, 5% 확률 500) — 로딩 스켈레톤·에러 상태를 실제로 확인

**데이터셋 설계 방침 — 낙관이 아니라 비관으로**

- 총 8,000건 — 예상 최종 규모와 동일하게 맞춰 성능을 실측합니다
- 지역 편중 — 강원·경북·충북에 몰리게 배치(자연휴양림 실제 분포). 균등 분포로 만들면 클러스터링 임계값을 낙관적으로 잡게 됩니다
- 극단 케이스 포함 — 20자 넘는 장소명, 좌표가 100m 내로 겹치는 쌍, 도서 지역 고립 핀
- 실제 장소명 + 합성 좌표 조합. 프로덕션 공개 API에서 `uid`/`title`/`trust_tier`를 수집하고 좌표만 합성하면 이름 길이·표기 편차가 현실적이라 레이아웃 깨짐을 미리 잡을 수 있습니다

### 5.2 지도 SDK 후보

> ✅ **2026-08-10 확정 — 네이버 지도** ([PRODUCT.md](../../PRODUCT.md) §6 D14, [map-explore-discussion.md](../../map-explore-discussion.md)).
> 아래 비교는 **웹 단독 기준**이라 카카오를 권장하고 있습니다. **RN 앱을 함께 보면 결론이 뒤집힙니다** — RN 래퍼 성숙도가 `@mj-studio/react-native-naver-map`(주 3,935 다운로드) 대 `@react-native-kakao/map`(주 69)으로 벌어지고, 웹·앱에 서로 다른 SDK를 쓰면 좌표·클러스터링 동작을 두 번 검증해야 합니다.
> 네이버는 클러스터러를 npm으로 제공하지 않아 `MarkerClustering.js`를 **vendoring**해야 합니다(Apache-2.0). 아래 표에서 카카오의 장점으로 적힌 "MarkerClusterer 내장"이 감수한 비용입니다.
> 이 절은 선정 경위 기록으로 남겨둡니다.

| 후보 | 장점 | 단점 |
|---|---|---|
| **카카오맵 JS v3** (권장) | `react-kakao-maps-sdk` 커뮤니티 래퍼가 성숙해 App Router 통합 비용이 가장 낮음, MarkerClusterer 내장, **지형도 레이어 확인됨(아래)** | 도메인 사전 등록 필요 |
| 네이버 지도 JS v3 | 국내 지형·등산로 표현이 가장 낫다는 평, 클러스터링 공식 예제 | npm이 아닌 스크립트 로드, 타입 비공식, React 래퍼 생태계 약함 |
| MapLibre GL JS + 국내 벡터 타일 | 오픈소스, 스타일을 완전히 커스터마이즈할 수 있어 `DESIGN.md` 토큰을 지도까지 적용 가능 | 국내 타일 소스 직접 구성 필요, 초기 셋업 비용 |

기획 초안이 지정한 **Mapbox는 채택하지 않습니다.** 한국 정밀 지도 반출 규제로 국내 상세도에 제약이 있고 유료입니다.

**검증 경과 (2026-08-06)** — 가리왕산(강원 정선, 1,561.8m)을 카카오맵에서 열어 확인했습니다.

- 기본 지도에서도 정상 표고, 중봉·하봉 등 봉우리, 임도갈림길·어은동 같은 **등산로 분기점이 지명으로 표시**되고 능선 경로가 선으로 이어집니다.
- **지형도 레이어**(지도설정 → 지형도)를 켜면 등고선 + 음영기복으로 능선·계곡 구분이 선명해집니다. 백패킹 후보지의 접근 난이도를 지도만 보고 가늠할 수 있는 수준입니다.

→ 초안이 카카오의 단점으로 적었던 "지형 표현이 약함"은 **지형도 레이어를 켜면 해소**됩니다. 다만 이 레이어를 JS SDK v3에서 켜는 방법(오버레이 맵타입 지정)은 SDK 연동 시점에 함께 확인해야 합니다.

> ~~⚠️ 미완 — 네이버 비교~~ → **종결.** 네이버지도는 자동화 브라우저 접근이 차단돼 같은 지점 비교를 못 했고, 결국 지형 표현이 아니라 **RN 래퍼 성숙도**가 결정 요인이 됐습니다(D14). 지형 관련 이월 숙제: 네이버 TERRAIN은 카카오와 달리 **오버레이가 아닌 배타적 베이스 타입**이라 음영기복 오버레이를 겹칠 수 없습니다. 대신 `LabelLayer`로 등산로 지명을 살릴 수 있는지 SDK 연동 시 확인해야 합니다.

| 항목 | 확정 결과 (2026-08-10) |
|---|---|
| 신규 필터 10종 | **폐기.** 필터 바는 계약이 지원하는 2종(카테고리 · 지역)으로 확정했습니다. `GET /v1/explore/spots`가 받는 필터는 `q`·`category[]`·`region_province`·`bbox` 4개뿐이고, [PRODUCT.md §4.3](../../PRODUCT.md#43-신뢰도상태-모델) 속성(화기·편의시설·예약/요금·접근성)에 대한 필터 계약은 존재하지 않습니다. **속성 필터는 MVP 이후.** 다중 선택·디바운스·초기화 메커니즘은 기존 `useSpotFilters`에 그대로 남습니다 |
| 정렬 | **MVP에 넣지 않습니다.** FTS 관련도순 고정 — `q` 있으면 랭킹 점수를 커서 `"s"` 키로 실어 관련도순, `q` 없으면 `{scope}:{uid}` 순. 정렬축으로 쓸 데이터가 없다는 것이 근거입니다: `trust_tier`가 191건 전부 2등급이고 평점·리뷰수는 미구현입니다. BE는 `_scope_token()`에 정렬 키를 넣을 수 있게 확장을 준비해뒀습니다 |
| 자동완성 | **MVP 제외.** 검색이 이미 PostgreSQL FTS + trigram이라 부분 매칭·오타 교정이 동작하고, 이것이 자동완성의 핵심 가치와 중복됩니다 |
| 미니카드 핵심 배지 | **제약 해소 — 배지 슬롯을 비워둘 이유가 없어졌습니다.** 축이 §4.3 **핵심 속성 4종(화기·편의시설·예약/요금·접근성)** 으로 확정됐습니다. 초안의 「합법·식수·취사·조용함」 4종은 폐기합니다 — 「합법」은 §4.4가 "합법 여부 판정이 아니라 확인 결과의 기록"으로 확정해 판정형 배지와 충돌하고, 「조용함」은 근거 필드도 판정 기준도 없으며, 「식수」는 편의시설의, 「취사」는 화기의 하위라 상위 축에 흡수됩니다. 값이 없으면 **슬롯 자체를 비웁니다** — "확인되지 않음" 같은 부정형 텍스트를 카드에 쓰면 카드가 부정형으로 덮입니다. 3등급 안전 속성을 "확인되지 않음"으로 일괄 표시하는 §4.3 기존 규칙은 **상세 화면 규칙**이라 여기에 적용되지 않습니다 |
| 카테고리 라벨 | **해소.** 아래 주석 참고. 옵션 공개 API는 여전히 없어 `packages/shared/src/constants/spotCategory.ts` 하드코딩은 유지합니다 |

> ✅ **해소** (2026-08-10 확인) — `searchFilterOptions.ts`가 `{ code, labelKo }` 분리 구조로 바뀌어 코드를 전송합니다. `regionFilterOptions`의 placeholder 4개(`경기·강원·충북·경남`)는 확정된 **17개 시도**로 교체하는 작업만 남았습니다.

**병목은 필터 계약이 아니라 데이터 적재로 옮겨갔습니다.** 필터 바가 계약된 2종으로 확정돼 상단 필터 바는 더 이상 블로커가 아닙니다. 남은 문제는 칩과 배지에 채울 값이 없다는 것입니다 — 전수 191건 기준 카테고리 3.7%, 썸네일 0%이고 나머지 수치는 [`STATUS.md`](../../STATUS.md) §7.2에 있습니다. 이 중 **category가 가장 싼 적재**입니다. 제목 기준으로 169건이 이미 자연휴양림으로 식별되므로(§7.3) 유추 적재만으로 채울 수 있고, 그러면 카테고리 필터와 카드 배지가 함께 살아납니다.

합법 여부 enum과 [`design/decisions/spot-detail-design-decisions.md`](../../../../vivac-frontend/design/decisions/spot-detail-design-decisions.md) §11.4.1의 3단계(초록/빨강/앰버) 전제를 맞춰야 한다는 기존 지적은 **그대로 유효합니다.** 위 결정은 「합법」을 **카드 배지 축에서만** 뺀 것이지 상세 화면의 합법 표시를 폐기한 것이 아닙니다 — 상세 화면의 합법 표시와 카드 배지는 별개 사안입니다.
