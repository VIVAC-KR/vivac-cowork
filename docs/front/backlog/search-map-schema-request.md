# 검색 지도 탐색(search-map) — BE 스키마 요청

- 작성일: 2026-08-04
- 목적: `GET /v1/explore/spots` 응답·파라미터 확장을 BE에 요청
- 배경: 검색 화면에 지도 기반 탐색(리스트/분할/지도 3개 모드)을 추가합니다. 현재 계약으로는 지도에 핀 하나도 그릴 수 없습니다.
- FE 설계 근거: [`docs/front/projects/search-map-explore.md`](../projects/search-map-explore.md)
- 선행 문서: [`docs/front/projects/search.md`](../projects/search.md) §4.3 참조 BE 계약

## 실측으로 확인한 현재 상태

2026-08-04 프로덕션 API를 직접 호출해 확인한 결과입니다.

| 확인 항목 | 결과 |
|---|---|
| `GET /v1/explore/spots` 지원 파라미터 | `q`, `category`, `region_province`, `cursor`, `limit` — 좌표·영역 관련 파라미터 없음 |
| `SpotListItem` 응답 필드 | `uid`, `title`, `trust_tier`, `thumbnail_url`, `region_short`, `category` — **좌표 없음** |
| `SpotDetail`의 `latitude`/`longitude` | 필드는 존재하나 샘플 3건 모두 **`null`** |
| 총 결과 개수 | 응답에 없음 (`next_cursor`·`has_more`만 존재) |

좌표는 수집 예정으로 확인했습니다. 아래 요청은 좌표 적재를 전제로 합니다.

## 요청 항목

### 1. `SpotListItem`에 좌표 필드 추가

| 필드 | 타입 | Nullable | 용도 |
|---|---|---|---|
| `latitude` | number (WGS84) | **N** | 지도 핀 렌더 |
| `longitude` | number (WGS84) | **N** | 지도 핀 렌더 |

**목록에 필요한 이유**: 상세에만 있으면 핀 20개를 그리는 데 상세 API를 20번 호출해야 합니다(N+1). FE 성능 목표(지도 이동 응답 100ms)를 이 구조로는 달성할 수 없습니다.

**non-nullable로 요청하는 이유**: 아래 3번(좌표 없는 스팟 제외) 결정에 따라 explore 응답에 도달한 항목은 좌표를 반드시 갖습니다. FE의 null 분기를 없애기 위해 스키마 레벨에서 보장받고자 합니다.

### 2. `bbox` 파라미터 추가

```
GET /v1/explore/spots?bbox=127.5,35.2,127.9,35.5
```

- 형식: `min_lng,min_lat,max_lng,max_lat` — 콤마 구분 단일 문자열, **경도 먼저**
- 의미: 지도 화면에 보이는 사각형 영역 안의 스팟만 반환

**필요한 이유**: 지도를 이동한 뒤 "이 지역 재검색" 버튼을 누르면 현재 화면 영역으로 재조회합니다. 지도 이동마다 자동 재검색하지 않는 것은 API 호출 폭증을 막기 위한 의도적 설계입니다.

**경도 우선 순서인 이유**: GeoJSON·OGC 표준 순서이며 지도 SDK의 bounds 객체에서 그대로 뽑아 쓸 수 있습니다. 다만 한국 좌표 범위(위도 33~38, 경도 124~132)는 서로 겹치지 않아, 순서를 잘못 쓰면 에러 없이 조용히 빈 결과만 반환됩니다. **API 문서에 순서를 명시**해주시면 좋겠습니다.

**다른 파라미터와의 조합**

| 조합 | 동작 |
|---|---|
| `q` + `bbox` | AND |
| `category` + `bbox` | AND |
| `region_province` + `bbox` | 발생하지 않음 — FE가 `bbox` 전송 시 `region_province`를 제거 |

`region_province`와 `bbox`는 의미가 충돌합니다(지도를 움직인 뒤에도 "강원" 필터가 남아 있으면 사용자 의도와 어긋납니다). 서버에 우선순위 규칙을 만들기보다 FE가 `bbox` 전송 시 `region_province`를 URL에서 제거하는 방식으로 정했습니다. 서버 규칙이 단순해지고, 검색 상태를 URL로 관리하고 있어 사용자도 필터 해제를 화면에서 확인할 수 있기 때문입니다. **서버는 두 값이 동시에 오는 경우를 방어하지 않아도 됩니다.**

**성능 참고**: 최종 스팟 규모가 8,000건 미만으로 예상됩니다. 이 규모에서는 PostGIS·GiST 인덱스나 서버 사이드 클러스터링이 과설계일 수 있습니다. 좌표 컬럼 인덱스 + 범위 조건으로 충분해 보이며, 판단은 맡기겠습니다.

### 3. 좌표 없는 스팟의 노출 제외

`latitude` 또는 `longitude`가 null인 스팟을 explore 계열 **전체**에서 제외합니다.

| 엔드포인트 | 동작 |
|---|---|
| `GET /v1/explore/spots` | 응답에서 제외 |
| `GET /v1/explore/spots/{uid}` | **404** |

**결정 이유**: 대안으로 "지도에서만 제외하고 리스트에는 노출 + 제외 건수를 응답에 포함"을 검토했으나 채택하지 않았습니다. 같은 검색 조건인데 리스트 모드와 지도 모드의 결과 집합이 달라지면, 사용자는 모드를 전환할 때마다 장소가 나타났다 사라지는 경험을 하게 됩니다. 백패킹 서비스에서 "이 장소가 실재하는가"에 대한 신뢰는 핵심 가치라, 노출 건수를 늘리는 것보다 **어느 모드에서 보든 같은 집합**이 보이는 정합성을 우선했습니다.

상세까지 404로 요청하는 이유도 같습니다. 목록에서만 빼면 북마크·공유된 상세 URL은 여전히 열려서, 검색으로는 찾을 수 없는 페이지가 링크로만 접근 가능한 상태가 됩니다.

**구현 방식은 위임합니다.** 발행 조건(`pipeline_status`)에 좌표 보유를 포함시키는 방식이 자연스러워 보이지만, 파이프라인 설계상 더 적절한 위치가 있다면 그쪽으로 부탁드립니다.

> ⚠️ **롤아웃 조건** — 현재 프로덕션 스팟은 좌표가 전부 null이라, 이 규칙을 지금 적용하면 탐색 결과가 0건이 됩니다. 좌표 수집 완료 후 적용하거나 플래그로 제어할 수 있게 해주세요. **좌표 적재 진행 상황과 예상 완료 시점 공유를 부탁드립니다** — FE 일정의 유일한 외부 의존입니다.

### 4. 총 개수 필드 추가

응답에 `total` 추가. 정확한 수치가 필요하지 않으므로 **상한 캡** 방식을 제안합니다.

```json
{ "items": [...], "next_cursor": "...", "has_more": true,
  "total": 1000, "total_capped": true }
```

**필요한 이유**: 리스트 헤더의 "N개 장소" 표기에 필요합니다. 현재 응답에는 총 개수가 없어, 지금 화면에 표시되는 "총 N곳"은 실제로는 현재 페이지 20건을 세고 있어 **이미 부정확합니다.**

**캡 방식인 이유**: 커서 페이지네이션에서 정확한 total은 매 요청 `COUNT(*)` 비용을 유발합니다. 사용자에게 필요한 정보는 "후보가 충분히 많다"이지 정확한 숫자가 아니라, 비용을 들여 정확도를 살 이유가 없다고 판단했습니다. **캡 임계값은 성능을 보시고 정해주세요.**

### 5. 지도용 경량 응답

지도 핀 렌더링에는 `uid`, `latitude`, `longitude`, `trust_tier`만 필요합니다. `thumbnail_url` 등 카드용 필드를 제외한 경량 응답이 필요합니다.

**형태는 위임합니다.** FE가 검토한 안은 `fields=map` 파라미터로 응답 필드를 줄이는 방식이었습니다(검색·필터 로직을 한 벌로 유지할 수 있어서). 별도 엔드포인트가 더 자연스럽다면 그쪽도 좋습니다. 핵심은 **핀 렌더링용 페이로드에서 무거운 필드를 빼는 것**입니다.

**`limit` 상한** — 당초 지도용 상한 500을 검토했으나, 전체 규모가 8,000건이면 **전국 단위로 줌 아웃했을 때 8,000건 전부가 `bbox`에 포함**됩니다. 이때 500건만 반환하면 지도가 실제보다 훨씬 비어 보이는 잘못된 정보를 주게 됩니다. 경량 응답이라면 8,000건이라도 gzip 후 100KB 안팎으로 예상되어, **지도용 응답은 상한을 8,000 수준으로 열어두고 클러스터링은 클라이언트에서 처리**하는 방안을 제안합니다. 실제 페이로드 크기를 측정해보시고 부담스러우면 알려주세요 — 줌 레벨별 서버 집계 등 대안을 함께 검토하겠습니다.

### 6. 커서와 bbox의 상호작용

요청의 `bbox`가 커서 발급 시점의 `bbox`와 다르면 **`400 CURSOR_SCOPE_MISMATCH`** 로 거부해주세요.

**결정 이유**: 지도를 움직인 뒤 이전 커서를 이어받으면 다른 영역의 위치를 가리켜 결과가 섞입니다. 서버가 조용히 커서를 무시하는 방식도 검토했으나, 그 경우 FE에서 "결과가 이상한데 에러는 안 남" 상태가 되어 원인 추적이 매우 어렵습니다. 명시적 에러가 FE 구현 부담(에러를 정상 흐름으로 처리)보다 낫다고 판단했습니다. FE는 이 에러를 받으면 커서를 버리고 처음부터 재조회합니다.

추후 정렬(`sort`)을 추가할 때도 정렬 키가 바뀌면 동일하게 커서를 무효화하는 규칙이 필요할 것으로 보입니다.

## 우선순위

| 순위 | 항목 | 없으면 |
|---|---|---|
| P0 | 좌표 데이터 적재 + 목록 응답 필드 추가 (1번) | 지도 개발 착수 자체가 불가 |
| P0 | `bbox` 파라미터 (2번) | 지도 탐색의 핵심 인터랙션 불가 |
| P1 | 지도용 경량 응답 + `limit` (5번) | 동작은 하나 성능 목표 미달 |
| P1 | 좌표 없는 스팟 제외 (3번) | 모드 간 결과 불일치 |
| P2 | `total` (4번), 커서 검증 (6번) | 표기 부정확, 엣지 케이스 |

FE는 위 계약대로 목(mock) 응답을 만들어 UI를 선행 구현합니다. **계약 형태만 확정되면 실제 구현 전이라도 병렬 진행이 가능하므로, 항목별 회신보다 계약 확정 여부를 먼저 알려주시면 좋겠습니다.**

## BE에 함께 확인받을 질문

1. 상세 API의 기존 `latitude`/`longitude`가 **WGS84(EPSG:4326)** 가 맞는지. 국내 지도 SDK는 WGS84 입력을 받지만 내부 좌표계가 달라, 여기가 어긋나면 핀이 통째로 엉뚱한 위치에 찍히고 증상이 "약간 틀림"이 아니라 "완전히 다른 곳"이라 조기 발견이 늦습니다.
2. 좌표 적재 방식 — 주소 기반 지오코딩이라면 **정확도 등급**(예: `EXACT` / `ROOFTOP` / `INTERPOLATED` / `REGION_CENTROID`)을 함께 내려줄 수 있는지. 오차가 큰 좌표를 UI에서 "대략적 위치"로 표기해 방어하려 합니다.
3. 좌표 적재 완료 예상 시점과 최종 스팟 건수 (현재 8,000건 미만으로 가정하고 설계 중입니다).
4. `region_short`·`category`·`thumbnail_url`이 실측에서 대부분 null이었습니다. 미수집 상태인지, 값이 없는 정상 상태인지 — FE의 placeholder 문구 결정에 필요합니다.

## 이번 요청에 포함하지 않은 것

아래는 계약이 확정되지 않아 별도로 요청드릴 예정입니다. [`search-map-explore.md`](../projects/search-map-explore.md) §6 참고.

- 필터 파라미터 (합법 여부, 식수, 취사, 조용함, 주차, 화장실, 데크, 백패킹, 고도, 거리)
- 정렬 `sort`
- 카테고리 옵션 공개 API — 현재 `spot_field_option`이 staff 전용(`/v1/internal/spot-options`)이라 FE가 라벨을 하드코딩 중이며, **한글 라벨을 코드 자리에 보내고 있어 기존 카테고리 필터가 동작하지 않는 상태**입니다
- 자동완성 `suggest` 엔드포인트
