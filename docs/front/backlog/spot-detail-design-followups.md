## 후속 논의가 필요한 사항 (기획 초안 섹션 9에 추가)

기획 초안 섹션 9(최진혁 협의 필요 사항)에 아래를 더한다.

1. **`특이사항` 필드에 구조화된 심각도(`severity`) 추가 여부** — 스펙 문서 섹션 4.1. 현재는 단일 톤 배너로 설계했지만, 실제로 "운영중단"류의 강한 경고와 "출입 시 주의"류의 약한 안내가 섞여 있다면 UI 차원의 3단계 배너가 유의미해진다.
2. **`전화/웹사이트/예약 링크` 3개 필드가 모두 `null`인 스팟의 비율** — 스펙 문서 섹션 7.3의 액션바 승격 규칙이 실효성 있는지 판단하려면 실데이터 분포가 필요하다.
3. ~~`DESIGN.md`의 색상/타이포 토큰을 `globals.css`에 정식 배선할지 여부~~ — **해결됨(v2).** 배선 완료. DESIGN.md가 단일 진실 공급원이다.
4. **한글 제목의 음수 자간 실기기 검수** — DESIGN.md display 토큰의 -0.96~-1.28px 자간은 라틴 알파벳 전제다. 한글에서 자소가 뭉쳐 보이는지 실기기(특히 저해상도 안드로이드)에서 확인이 필요하다. 문제가 확인되면 `:lang(ko)` 스코프로 자간을 완화하는 예외 규칙을 `globals.css`에 추가하는 방안을 검토한다 — 이 경우 DESIGN.md의 *"음수 자간은 브랜드 목소리의 일부"* 규칙과 충돌하므로 명시적 결정이 필요하다.
5. ~~`success` = 파랑 정책의 재검토~~ — **해결됨.** DESIGN.md Don't를 명시적으로 어기고 초록을 6번째 액센트로 추가했다(편차 #1, 의사결정 기록 §11.4.1). **다만 새 후속 과제가 생겼다** → 7번.
6. **다크 램프 대비비 실측** — ~~DESIGN.md에 다크 팔레트가 없어 직접 파생한 값이다. WCAG AA(4.5:1) 검증이 필요하며, 특히 `text-mute` on `bg-canvas`, `text-warning-deep` on `bg-warning-soft` 조합을 우선 확인한다.~~ **해결됨(v2.2, 2026-07-15).** 실측 결과는 스펙 문서 §10 참고. `mute` on `canvas`가 라이트 모드에서 3.54:1로 AA 미달 확인 — 본문 텍스트 사용 금지 제약을 스펙에 반영함. 다크 `error-deep` 버그(1.3:1)도 이때 발견해 수정.
7. **적록색맹 대응 검증** — 편차 #1로 legalStatus가 초록/빨강 조합을 쓰게 됐다. 적록색맹(남성 약 8%) 사용자에게 "허가됨"과 "금지됨"이 구분되지 않는다. 현재는 텍스트 라벨 병기로만 완화하고 있다(스펙 문서 §10). 색맹 시뮬레이터로 실검증하고, 필요하면 아이콘 형태 차이(체크/금지 표식)를 추가하는 방안을 검토한다.

## 부록 A. 실제 API 스키마 대조 (참고용, 확정 아님)

프로젝트 루트의 `.openapi.json`(날짜 미상, WIP 스냅샷으로 추정)을 대조한 결과다. **정식 확인 절차 없이 발견한 파일**이므로 스펙 문서의 결정 근거로 직접 인용하지 않았고, Props 시그니처의 필드명 추정에만 참고했다. 아래는 그대로 인용한 팩트다.

- `GET /v1/explore/spots/{uid}` 응답 스키마(`SpotDetail`)는 현재 `uid`, `title`, `address`, `website_url` **4개 필드만** 정의돼 있다 — 기획 초안이 전제하는 21개 필드 중 극히 일부만 실제 조회 API에 노출된 상태다.
- 반면 ETL 벌크 적재 스키마(`SpotBulkRow`)에는 `unit_count`, `total_area_m2`, `camp_sight_type`, `category`(배열), `themes`(배열), `fire_pit_type`, `amenities`(배열), `nearby_facilities`(배열), `has_equipment_rental`(배열), `is_fee_required`, `is_pet_allowed`, `pet_policy`, `website_url`, `booking_url`, `phone`, `latitude`/`longitude`, `tagline`, `description`, `features`, `rating_avg`(기본값 0), `review_count`(기본값 0) 등 기획 초안 필드 대부분과 대응하는 이름이 이미 존재한다.
- 특히 `rating_avg`/`review_count`가 데이터 모델 상 **기본값 0으로 이미 정의**돼 있다는 점은 눈여겨볼 만하다 — 기획 초안은 "리뷰/평점 필드 자체가 없다"고 전제했지만, 데이터 모델 레벨에서는 필드가 이미 존재하고 단지 실제 리뷰가 없어 값이 0인 상태일 가능성이 있다. 이게 사실이라면 "필드 부재(수집 예정)"이 아니라 "0건"이라는 **정상 데이터 상태**로 다뤄야 할 수도 있다(예: "아직 리뷰가 없어요" vs "평점 0.0 · 리뷰 0건"). 이 구분은 실제 조회 API가 이 필드를 언제, 어떤 값으로 내려주는지 확인되기 전까지는 단정할 수 없다.
- `SpotDetail`과 `SpotBulkRow`의 간극(4개 vs 30여 개)은 M3(BE API 엔드포인트) 작업이 아직 적재 스키마만큼 조회 API를 완성하지 못한 상태임을 보여준다 — 이는 P1-1-B(장소 탐색 UI)가 M3에 의존한다는 기획 문서의 의존성 표와 정확히 들어맞는 정황이며, 이 상세페이지가 "부분 결측을 전제로 설계해야 한다"는 스펙 문서의 접근(섹션 8.3)이 필요한 이유를 뒷받침한다.
