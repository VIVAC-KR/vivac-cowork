# Linear 프로젝트 등록 형식

Linear에 project를 만들거나 description을 채울 때(`mcp__claude_ai_Linear__save_project` 등) 본문은 아래 섹션 구성을 따름. 이모지·말투는 [linear-issue-format](./linear-issue-format.md)과 맞추되, 섹션 구성 자체는 프로젝트 스코프(여러 이슈를 묶는 상위 단위)에 맞게 다르게 구성함.

이슈 description은 개발자가 구현할 때 참고하는 문서라 기술 용어를 그대로 씀. 반면 **프로젝트 title/description은 PM·기획자가 읽는 문서** — 엔드포인트 경로, 함수명, 파일 경로, 클래스명 등 구현 디테일은 배제하고, 유저(또는 관리자·운영팀 등 실제 사용 주체)가 체감하는 기능 단위로 씀. 기술 디테일이 필요하면 서술하지 말고 관련 이슈 링크로 위임.

이름이 `(Ongoing)`으로 끝나는 지속형 프로젝트(끝이 정해지지 않고 계속 굴러가는 운영·유지보수성 프로젝트)에는 아래 Title 규칙을 적용하지 않음 — 완료 시점 자체가 없어 능력 서술문으로 지을 대상이 아님.

## Title 규칙

프로젝트 이름은 "OO 기능", "XX 개선" 같은 카테고리 라벨이 아니라, **이 프로젝트가 끝났을 때 참이 되는 문장(능력/성과 서술문)** 으로 짓는다. 완료 여부를 프로젝트 이름만 보고도, 그리고 `Related Issues`의 완료/미완료 개수로 정량적으로 판단할 수 있어야 한다.

- 사용자 대상 기능이면 실행 주체를 명시: `유저는 ~할 수 있습니다`, `관리자는 ~할 수 있습니다`
- 내부 안전장치/리스크 개선처럼 실행 주체가 유저가 아니면, 무엇이 어떤 상태가 되는지로 서술: `OO가 XX로부터 안전하게 보호됩니다`, `OO가 YY 없이 정확하게 집계됩니다`
- 나쁜 예: `DM/채팅`, `이미지 업로드 S3 비용/보안 개선` — 무엇을 다루는지는 알지만 언제 끝났다고 할 수 있는지 알 수 없음
- 좋은 예: `유저는 다른 유저와 1:1 또는 그룹으로 실시간 채팅할 수 있습니다`, `스팟 이미지 업로드가 용량·개수·요청 남용으로부터 안전하게 보호됩니다`

## 본문 템플릿

```markdown
## 🎯 Goal

## 🗺️ Background

## 📌 Scope
### In Scope
* 

### Out of Scope
* 

## 🔗 Related Issues
> 

## Notes
* 
```

- 섹션 순서·이모지·제목 문구 그대로 유지. 내용 없는 섹션도 헤더는 남김(빈 채로 두거나 "해당 없음")
- 기술 용어(함수명, 엔드포인트, 필드명 등)는 영문 그대로, 코드 인용은 백틱으로 표기
- 서비스명은 항상 `vivac`/`VIVAC`, 한글 표기(비바크, 비박 등) 금지

## 섹션별 작성 기준

- `Goal`: 프로젝트에 묶인 이슈들을 관통하는 상위 목표 1~2문장. 개별 이슈의 Goal을 나열하지 않음. 위 Title 규칙과 같은 시점(완료 시 무엇이 가능해지는지) 기준으로 씀
- `Background`: 이슈 포맷에는 없는 섹션. 왜 지금 이 프로젝트가 필요한지 — 유저/비즈니스 관점의 계기와 배경 상황, 관련된 다른 프로젝트/이슈와의 연결. "어떻게 구현했는지"가 아니라 "왜 시작됐는지"를 씀
- `Scope`: 프로젝트 범위. In Scope 항목은 `유저는/관리자는 ~할 수 있다` 식으로 기능을 체감 단위로 쓰고, 항목마다 관련 이슈 링크를 `([XXX-123](URL))` 형태로 함께 표기. 엔드포인트·파일 경로·클래스명 등은 쓰지 않음 — 필요하면 이슈 링크를 따라가서 보게 함
- `Related Issues`: 프로젝트에 속한 이슈를 `> [XXX-123](URL) — 한 줄 설명 (담당 영역, 상태)` 형태로 나열. 완료 여부는 체크박스가 아니라 상태 표기(Done/In Progress/Todo/Backlog/Triage 등)로 표현 — 프로젝트는 이슈처럼 단일 완료 조건이 아니라 여러 이슈의 진행 상태 모음이기 때문. 이 목록의 Done 비율이 곧 프로젝트 진척도
- `Notes`: 프로젝트 진행 중 알게 된 맥락, 후속 이슈로 분리된 사항, 팀 간 조율 내용, 전체 이슈 대비 완료 개수(예: "2/2 이슈 완료 — 프로젝트 완료 상태") 등

이슈 포맷에 있는 `Acceptance Criteria`는 프로젝트에는 두지 않음 — 프로젝트 완료 여부는 `Related Issues`의 상태로 판단하므로 별도 체크리스트가 중복됨.

Project 설명 작성 전 프로젝트에 할당된 issue 목록을 먼저 확인하고, 그 내용을 근거로 작성.
